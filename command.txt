PROJECT: Multi-Tenant SaaS Platform (Database-per-Tenant Architecture)

## Overview
Build a multi-tenant business management platform where each company (tenant) gets its own
dynamically provisioned, isolated database. A Superadmin can manage all tenants from a single
control panel, while each company's users only ever see and operate on their own company's data.

## Tech Stack
- Frontend: React (latest), with dynamic routing per tenant
- Backend: Django + Django REST Framework
- API Docs: drf-yasg or drf-spectacular (Swagger/OpenAPI), routes grouped by module/app
- Database: PostgreSQL (recommended for schema-per-tenant or database-per-tenant isolation)

## Core Architecture: Tenant Isolation

1. **Central/Public Database**
   - Stores the tenant registry: company_id, company_name, company_slug (used in URLs),
     company_owner details, company_logo, db_connection_info, status (active/suspended),
     selected_modules, created_at.
   - Superadmin credentials and audit logs also live here.

2. **Per-Tenant Database (dynamic provisioning)**
   - When a company is onboarded via the configuration form, the backend should:
     a. Validate company details (name uniqueness, slug uniqueness).
     b. Dynamically create a new database (or schema) for that company.
     c. Run migrations against the new database to create tenant-scoped tables
        (Employees, Customers, and any tables tied to the selected modules).
     d. Register the new tenant + its DB connection details in the central database.
     e. Provision the company's initial admin/owner user inside that tenant DB.
   - Use Django's multi-database support (`DATABASE_ROUTERS`) or a library such as
     `django-tenants` / `django-tenant-schemas` to route requests to the correct
     database based on the resolved tenant context per-request.
   - All CRUD operations for employees, customers, and module-specific masters must be
     executed against the correct tenant DB — never the central DB.

3. **Superadmin Capabilities**
   - Superadmin logs in via a fixed, non-tenant route: `/__superadmin` (credential-gated).
   - From the superadmin panel, superadmin can:
     - View/search all tenants and their status.
     - Open/impersonate a tenant context to view or edit that tenant's data directly
       in its own isolated database (edits made "on behalf of" a tenant must persist
       only in that tenant's DB, not the central DB).
     - Suspend/reactivate/delete a tenant (with safeguards — deletion should be a
       soft-delete or explicitly confirmed hard action).
     - View which modules are enabled per tenant.

## Middleware & Multi-Database Connection Management
- `TenantResolverMiddleware` (runs early in `MIDDLEWARE`):
  1. Extracts the tenant identifier from the incoming request — company slug in the URL
     path (or subdomain, or an `X-Tenant` header for API clients).
  2. Looks up the tenant's DB connection info from the central DB (cache this lookup,
     e.g. in Redis or Django cache, to avoid a central-DB hit on every request).
  3. Registers/activates that tenant's DB connection alias for the duration of the
     request (see below), and attaches `request.tenant` (slug, company_id, enabled
     modules, active field-set) for use by views/serializers.
  4. Rejects the request (404/403) if the slug doesn't resolve to an active tenant, or
     if the tenant is suspended.
  5. Bypasses tenant resolution entirely for `/__superadmin` and central-DB-only routes.
- Django `settings.DATABASES` cannot be edited at runtime by default, so new tenant
  connections must be injected dynamically:
  - On app startup, load all existing tenant DB configs from the central DB into
    `settings.DATABASES` (keyed by tenant slug/id as the alias).
  - When a new tenant is provisioned, add its connection to `settings.DATABASES` in
    memory (and persist the config so it reloads correctly on the next process restart/
    worker reload) — e.g. `django.db.connections.databases[alias] = {...}`.
  - Pair this with a custom `DATABASE_ROUTERS` class that:
    - Routes central models (`Tenant`, `TenantModule`, `SuperAdminUser`, `FieldCatalog`)
      to the `default`/central DB always.
    - Routes tenant-scoped models (`Employee`, `Customer`, module models) to
      `request.tenant`'s DB alias, using a thread-local/contextvar set by the middleware
      (since routers don't get direct access to the request).
- Add a `TenantContextMiddleware` step (or fold into the resolver) that clears the
  thread-local/contextvar at the end of each request to avoid leaking tenant context
  across requests in the same worker.

## Per-Tenant Migrations & `migrate`
- Each tenant DB needs its own migration history, independent of other tenants, because
  tenant schemas can diverge (see Field-Level Dynamic Schema below).
- Provide a management command, e.g. `manage.py migrate_tenant <company_slug>`, that:
  - Resolves the tenant's DB alias.
  - Runs `call_command('migrate', database=alias)` scoped to the tenant apps only
    (`employees`, `customers`, and any module apps) — central apps never migrate here.
- Provide `manage.py migrate_all_tenants` to loop over every active tenant and run the
  above (used after deploying a new migration that must roll out to every company).
- On new tenant provisioning, the provisioning service (not manual `migrate`) triggers
  `migrate_tenant <new_slug>` automatically right after DB creation.
- Because Employee/Customer fields vary per tenant (see below), "migrations" for those
  two tables are not static Django migration files shared by all tenants — instead:
  - Keep a fixed "core" migration (id, timestamps, tenant-safe base columns) that is
    identical for every tenant.
  - Layer tenant-specific columns on top via a dynamic schema step (raw
    `ALTER TABLE ... ADD COLUMN` via `SchemaEditor`, executed per tenant based on that
    tenant's chosen fields) rather than one Django migration file per tenant.
  - Track which fields/columns exist per tenant in a metadata table (see Field-Level
    Schema) so the system always knows the current shape of each tenant's table without
    inspecting the DB directly.

## Field-Level Dynamic Schema (Employee & Customer Masters)
Problem: different companies need different fields on the same logical table — e.g.
Tata's Employee master uses 8 fields, Tesla's uses 14 — but all valid fields are
predefined and controlled by Superadmin, not freely typed by tenants.

- **Master Field Catalog** (central DB): `FieldCatalog` model defining every field
  Superadmin has made available per entity type, e.g.:
  - `entity` (`employee` / `customer`), `field_key`, `label`, `data_type`
    (string/int/date/bool/enum/etc.), `is_required_default`, `options` (for enums),
    `created_by_superadmin`.
  - This is the single source of truth — e.g. 14 fields defined for `employee`.
- **Tenant Field Selection**: `TenantFieldConfig` model (central DB) mapping
  `(tenant, entity, field_key) -> enabled (bool), is_required, order`.
  - Superadmin (or the company owner, if allowed) picks which subset of the catalog
    applies to that tenant — Tata enables 8 of the 14 employee fields, Tesla enables
    all 14.
  - This selection is part of the same configuration form used for onboarding (extend
    it with a per-module field checklist once Employees/Customers modules are chosen),
    and can be edited later from the Superadmin panel or tenant admin settings.
- **Applying the selection to the tenant DB**:
  - A `TenantSchemaSyncService` compares a tenant's current `TenantFieldConfig` against
    the actual columns present in that tenant's `Employee`/`Customer` table.
  - Missing enabled fields → add the column (`ADD COLUMN`) with the catalog's data type.
  - Disabled fields that still have a column → either drop the column or simply hide it
    at the serializer/UI layer (prefer soft-hide + nullable to avoid destructive data
    loss unless the user explicitly requests a hard removal).
  - This sync runs automatically right after tenant provisioning and again whenever a
    tenant's field selection is updated.
- **Dynamic serializers/forms**: Since the field set is data-driven, Employee/Customer
  DRF serializers and React forms should be built dynamically from `TenantFieldConfig`
  for the current tenant (fetched via an API like `/api/schema/employee/` returning the
  active fields, types, and required flags) rather than hardcoded per-field definitions.
- **Model storage strategy** — pick one and apply consistently:
  - Option A (recommended for true per-tenant DBs): real dynamic columns via
    `SchemaEditor.add_field`/`remove_field`, keeping each tenant's table shape exact.
  - Option B (simpler, less isolation-pure): fixed core columns + a JSONField
    (`extra_fields`) holding the tenant's enabled catalog fields as key/value pairs,
    validated against `TenantFieldConfig` at the serializer level. Faster to build, no
    schema migrations needed per field change, but loses native DB-level typing/
    indexing on those fields.

## Tenant Onboarding — Configuration Form
A form (superadmin-facing, or self-service signup) that collects:
- Company Name
- Company Slug (auto-suggested from name, editable, used for the dynamic URL)
- Company Owner (name, email, phone)
- Company Logo (image upload)
- Module Selections (checklist — e.g. Employees, Customers, Inventory, Billing, etc.)

On submit, this triggers the dynamic DB provisioning flow described above, and only the
modules selected should have their corresponding tables/routes/menus activated for that
tenant going forward.

## Frontend Routing (React)
- Dynamic tenant-aware URLs based on company slug, e.g.:
  - `/<company-slug>/login` — tenant-specific login page (can show the tenant's logo/branding)
  - `/<company-slug>/dashboard`, `/<company-slug>/employees`, `/<company-slug>/customers`, etc.
- A dedicated Superadmin login route: `/__superadmin`
  - NOTE: Do not hardcode the password ("28042003") into the frontend or committed code.
    Store superadmin credentials securely (hashed, in the backend DB / environment secrets)
    and authenticate via a normal secured login API — treat this as sensitive.
- On app load, resolve the slug from the URL to determine which tenant's branding/config
  to fetch (public info only, e.g. logo/company name) before login.
- After login, store the tenant context (slug/company_id) in the auth token/session so
  all subsequent API calls are scoped to the correct tenant automatically.

## Backend (Django)
- Apps structured by domain (e.g. `tenants`, `employees`, `customers`, `modules`, `core_auth`).
- Central models: `Tenant`, `TenantModule`, `SuperAdminUser` (or reuse Django's auth with a role flag).
- Tenant-scoped models: `Employee`, `Customer`, and models for each selectable module.
- Middleware to resolve the active tenant from the request (subdomain, URL slug, or header)
  and bind the correct DB connection for the duration of the request.
- API routing grouped logically per module (e.g. `/api/employees/`, `/api/customers/`,
  `/api/tenants/`, `/api/auth/`), each with its own DRF router registered under a common
  API root.
- Swagger/OpenAPI docs enabled (drf-yasg or drf-spectacular) with endpoints grouped by tag
  matching the module/app structure, so the API docs mirror the router grouping.
- Auth: JWT or session-based, with a distinct permission class/flow for Superadmin vs.
  tenant users vs. tenant owner/admin.

## Security Considerations
- Never expose raw DB connection strings or credentials to the frontend.
- Enforce strict tenant-boundary checks on every query — a user authenticated for
  Company A must never be able to read/write Company B's database, including via
  the superadmin impersonation flow (log all superadmin cross-tenant actions for audit).
- Superadmin credentials must be stored hashed and managed via environment secrets,
  not hardcoded.
- Validate/sanitize company slug input (used in URLs and possibly DB/schema names) to
  prevent injection into DB identifiers.

## Deliverables (suggested build order)
1. Central DB schema + `Tenant`/`TenantModule`/`FieldCatalog`/`TenantFieldConfig` models.
2. Dynamic DB/schema provisioning service (create DB, run tenant migrations, register tenant).
3. `TenantResolverMiddleware` + `DATABASE_ROUTERS` + thread-local tenant context.
4. `migrate_tenant` / `migrate_all_tenants` management commands.
5. Superadmin auth + panel (list tenants, view/edit tenant data, enable/disable modules,
   manage the master `FieldCatalog`, assign per-tenant field selections).
6. Tenant configuration/onboarding form, including per-module field checklist
   (backend API + frontend form).
7. `TenantSchemaSyncService` to apply field selections as real schema changes per tenant.
8. Module-driven Employee/Customer masters with dynamic, tenant-specific fields
   (tenant-scoped CRUD + dynamic serializers/forms driven by `TenantFieldConfig`).
9. React dynamic routing per company slug + tenant-branded login pages.
10. Superadmin login route (`/__superadmin`) with secure credential handling.
11. Swagger docs with grouped routers across all modules.
