Engineering brief: API naming convention, config-driven modules, backend
restructure, and Superadmin Dashboard/entity-code enhancements
(Tenant Architecture platform — Django backend + React/Vite/Tailwind frontend)
================================================================================

This replaces the earlier scratch notes in this file with one consolidated,
actionable brief. It assumes the current state of the repo: a services/
layer already exists on the frontend (src/services/*.js), the UI redesign
pass is done, and the backend has database-per-tenant multi-tenancy with
dynamic Employee/Customer schemas. The items below are the next slice of
work, grounded in the actual files in this repo.


1. API method naming convention — CRUD verbs, not list/remove
--------------------------------------------------------------
Every service-layer helper must expose the same five methods, named after
the operation, not after REST/HTTP jargon:

    create        (POST)
    read          (GET — collection, i.e. today's "list")
    readById      (GET — single record by id, i.e. today's implicit "retrieve")
    update        (PUT/PATCH)
    delete        (DELETE — today's "remove")

Rename in place, keep the underlying endpoints unchanged:

  - src/services/entityService.js — createEntityService(slug, entity) currently
    returns { getSchema, list, create, remove }. Rename list -> read,
    remove -> delete, and add a readById(id) method
    (apiClient.get(`${base}/${id}/`)). Keep getSchema as-is (it isn't a CRUD verb).

  - src/services/tenantsService.js — rename list -> read and add readById(id)
    (apiClient.get(`/superadmin/tenants/${id}/`)). create/suspend/reactivate
    stay; nested resources (getModules/updateModules, getFieldConfig/
    updateFieldConfig, getTableLimits/updateTableLimits, getUsers/createUser)
    should follow the same read/create/update/delete naming per sub-resource
    (e.g. getUsers -> readUsers, createUser -> createUser is already fine
    since it's already a create verb — just don't reintroduce list/get-only
    naming for anything new).

  - src/services/fieldCatalogService.js — rename list -> read, add readById.

  - Every call site (DashboardPage.jsx, FieldCatalogPage.jsx, CompanyUsersPage.jsx,
    CompanyFieldConfigPage.jsx, CompanyLimitsPage.jsx, OnboardCompanyPage.jsx,
    EntityManager.jsx) must be updated to call the renamed methods — grep the
    frontend for `.list(` and `.remove(` after the rename to make sure nothing
    is left calling the old names.

  - Backend mirror: DRF ViewSet actions already map to list/retrieve/create/
    update/partial_update/destroy under the hood (that's fine — it's DRF's
    own routing convention and doesn't need to change). The naming convention
    above is a *frontend service-layer* convention so every module's helper
    has an identical, predictable shape — it does not require renaming DRF
    viewset methods.


2. Config-driven modules & plans — single source of truth
------------------------------------------------------------
Right now the module list is duplicated by hand in several places:
  - AVAILABLE_MODULES is hardcoded inside OnboardCompanyPage.jsx
  - MODULE_TO_ENTITY is hardcoded inside CompanyFieldConfigPage.jsx
  - ENTITY_TO_MODULE_KEY / MODULE_CHOICES already exist as the backend's
    static source of truth in backend/tenants/entities.py

Fix: create ONE frontend config file, src/config/modules.js, that mirrors
backend/tenants/entities.py exactly:

    export const AVAILABLE_MODULES = [
      { key: 'employees', entity: 'employee', label: 'Employees',
        description: 'Employee records and employee-specific fields.' },
      { key: 'customers', entity: 'customer', label: 'Customers',
        description: 'Customer records and customer-specific fields.' },
    ];

    export const PLAN_INFO = {
      basic:      { label: 'Basic',      hint: 'Login + read-only access to all data.' },
      enterprise: { label: 'Enterprise', hint: 'Login + full CRUD (create, read, update, delete).' },
    };

Then:
  - OnboardCompanyPage.jsx imports AVAILABLE_MODULES from this file instead
    of defining its own copy.
  - CompanyFieldConfigPage.jsx derives MODULE_TO_ENTITY from AVAILABLE_MODULES
    (`Object.fromEntries(AVAILABLE_MODULES.map(m => [m.key, m.entity]))`)
    instead of hand-maintaining a second mapping.
  - Navigation, routes, and each module's entityService instance
    (createEntityService(slug, module.entity)) should be generated by
    iterating AVAILABLE_MODULES — adding a third module later means adding
    one entry to this array and to backend/tenants/entities.py, nothing else.
  - Plan gating: wherever CRUD buttons are shown (EntityManager's "Add"
    form/button, the per-row Delete link), hide/disable create/update/delete
    controls when the current tenant's plan is 'basic' (read + readById only),
    matching the backend's existing IsTenantUserOrSuperAdmin read-only
    enforcement for Basic-plan tenants (backend/core_auth/permissions.py) —
    this should be a UI-level mirror of a rule the backend already enforces,
    not a new rule.
  - Respect the selected max-records option (the MAX_RECORDS_OPTIONS dropdown
    already used in CompanyLimitsPage.jsx / OnboardCompanyPage.jsx) by passing
    it through as the page size when fetching that table's records, instead
    of only using it as a stored server-side cap.


3. Backend restructure — split tenants/{models,serializers,views}.py by schema
--------------------------------------------------------------------------------
backend/tenants/models.py currently holds 7 unrelated model classes in one
179-line file (Tenant, TenantModule, TenantTableLimit, FieldCatalog,
TenantFieldConfig, SuperAdminUser, TenantAuditLog), and
tenants/serializers.py / tenants/views.py are similarly monolithic. Split
each into a package, grouped by what the model/serializer/view is actually
about, mirroring the module system described in section 2:

    backend/tenants/
    ├── models/
    │   ├── __init__.py        # re-exports every model so `from tenants.models import Tenant` keeps working
    │   ├── tenant.py           # Tenant, TenantModule
    │   ├── limits.py           # TenantTableLimit
    │   ├── field_catalog.py    # FieldCatalog, TenantFieldConfig
    │   ├── superadmin.py       # SuperAdminUser
    │   └── audit.py            # TenantAuditLog
    ├── serializers/
    │   ├── __init__.py
    │   ├── tenant.py
    │   ├── limits.py
    │   ├── field_catalog.py
    │   └── users.py            # the nested /users/ read/create serializer
    ├── views/
    │   ├── __init__.py
    │   ├── tenant.py            # TenantViewSet (create/read/readById/update/delete + modules/field-config/table-limits/users actions)
    │   └── field_catalog.py     # FieldCatalogViewSet
    ├── entities.py              # unchanged — already the single source of truth for ENTITY_TO_MODULE_KEY/MODULE_CHOICES
    ├── urls.py                  # unchanged — registers the split viewsets via the same router
    └── ...                      # dynamic_models.py, schema_sync.py, context.py, mixins.py, limits.py (app logic) stay as-is

Migration mechanics:
  - Converting models.py -> models/ is a pure code-organization change;
    Django migrations key off app_label + model name, not file path, so this
    does NOT require a new migration as long as every model keeps its
    existing `class Meta: app_label = 'tenants'` (or app default) and
    fields/table names are untouched.
  - Run `manage.py makemigrations --check --dry-run` after the split to
    confirm Django sees zero schema changes — if it proposes anything,
    something's field/meta was altered by accident during the move.
  - Update every internal import (`from tenants.models import Tenant, ...`)
    across the codebase — models/__init__.py re-exporting everything means
    most call sites need no change at all.
  - modules/employees/ and modules/customers/ are already split per-schema
    (separate apps, each with its own small models.py/serializers.py/views.py)
    — use that as the reference shape for the tenants/ package split above,
    don't restructure those two apps further.


4. Superadmin Dashboard (frontend/src/pages/superadmin/DashboardPage.jsx)
-----------------------------------------------------------------------------
  - Full width: change `maxWidth="max-w-6xl"` to a wider/full-bleed layout
    (e.g. `max-w-7xl` or `max-w-full` with horizontal padding) so the
    companies table uses the full viewport on desktop instead of being
    constrained — this table has 7 columns (Company, Login URL, Owner,
    Modules, Tier/Plan, Status, Actions) and is currently the most
    column-dense table in the app.
  - Page size: replace the hardcoded `const PAGE_SIZE = 20` with a
    configurable dropdown next to the search box, options matching the
    style of MAX_RECORDS_OPTIONS elsewhere (e.g. 6 / 10 / 20 / 50 / 100 per
    page, default 6 as requested), stored in component state
    (`const [pageSize, setPageSize] = useState(6)`), passed through to
    tenantsService.read({ page, page_size: pageSize, search }), and reset
    page to 1 whenever pageSize changes (same pattern already used for the
    debounced search term). This requires the backend TenantViewSet's
    pagination class to honor a `page_size` query param (DRF's
    PageNumberPagination supports this via `page_size_query_param` — set
    `page_size_query_param = 'page_size'` and a sane `max_page_size` on
    whatever pagination class TenantViewSet uses).


5. Tenant-scoped auto-generated employee/customer codes
-----------------------------------------------------------
Add a human-readable, tenant-scoped, auto-incrementing identifier to both
Employee and Customer records — shown as its own column in EntityManager's
table (frontend/src/pages/modules/shared/EntityManager.jsx) for both entities.

Format: `{tenant-slug}-{ENTITY-PREFIX}-{sequence}`, e.g.
  nike-EMP-001, nike-EMP-002, ... for Employees
  nike-CUST-001, nike-CUST-002, ... for Customers

  - Backend: add a `code` field to both modules/employees/models.py's
    Employee model and modules/customers/models.py's Customer model
    (CharField, unique per tenant DB — since each tenant already has its own
    physical database, uniqueness is automatically per-tenant with no extra
    scoping needed). Populate it on create by looking up the current max
    sequence for that table in that tenant's DB and incrementing — do this
    in the ViewSet's perform_create (modules/employees/views.py,
    modules/customers/views.py) or in TenantEntityViewSetMixin
    (tenants/mixins.py) if the logic should be shared across both entities,
    not client-generated, so two concurrent creates can't collide (wrap the
    max-lookup + insert in a transaction, or use a per-tenant counter row,
    to avoid a race between the SELECT MAX and the INSERT under concurrent
    requests).
  - Prefix per entity comes from a small constant map (EMP for employee,
    CUST for customer) — keep this next to ENTITY_TO_MODULE_KEY in
    backend/tenants/entities.py so it's alongside the other entity metadata.
  - This new `code` column needs the same ALTER TABLE treatment as any other
    dynamic column — either add it via schema_sync.py's sync path so it's
    provisioned consistently for every existing tenant DB, or a one-off
    migration + backfill script that assigns codes to any pre-existing rows
    before the column becomes NOT NULL/UNIQUE.
  - Frontend: EntityManager's schema-driven table already renders one <th>/
    <td> per field returned from GET /<slug>/<entity>/schema/ — once the
    backend schema endpoint includes `code` as a field, no separate frontend
    change is needed beyond making sure it renders first/leftmost and is
    read-only (never shown in the "Add" form, since it's server-generated,
    not user-entered).


Deliverable
-----------
A services layer with one consistent CRUD-verb interface across every
module, one shared frontend module/plan config that mirrors the backend's
entities.py, a tenants/ backend package split by schema (models/
serializers/views each broken into per-concern files, zero migration diff),
a wider and page-size-configurable Superadmin companies dashboard, and
tenant-scoped human-readable codes on Employee/Customer records end to end.
