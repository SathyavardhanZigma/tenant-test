Based on your answers, I would **not** build the tenancy configuration as a huge flat collection of checkboxes.

You need a **hierarchical capability/configuration system** where Zigma defines the maximum product experience available to a tenant, and the tenant later manages its own staff/user permissions *inside that boundary*.

That gives you a universal model that can handle requests like:

* “Give me the map, but remove Ward filter.”
* “Show only 4 KPI cards.”
* “Hide fullscreen on the map.”
* “Make the map larger.”
* “Put complaints above attendance.”
* “Show collection progress for 7 days instead of 31.”
* “Give us Grievances module but not grievance summary on dashboard.”
* “We bought Standard now; upgrade us to Advanced.”
* “Add a new dashboard widget next year.”

without redesigning tenancy every time.

## 1. The overall model I recommend

Think of tenant configuration as **five separate concerns**:

```text
TENANT CONFIGURATION
│
├── 1. PRODUCT ENTITLEMENT
│      What modules/features has Zigma given this tenant?
│
├── 2. UI COMPOSITION
│      What appears on each page/dashboard?
│
├── 3. COMPONENT CONFIGURATION
│      How does each visible component behave?
│
├── 4. DATA SCOPE
│      What business/geographical data can this tenant access?
│
└── 5. TENANT-OWNED USER PERMISSIONS
       Inside what Zigma enabled, what can each tenant user access?
```

That separation is the key.

# 2. Your Zigma/Tenant responsibility model

Your idea is correct, with one refinement.

### Zigma controls the tenant ceiling

Zigma decides:

```text
Tenant has Dashboard             YES
Tenant has Grievances            YES
Tenant has Reports               YES
Tenant has Route Optimization    NO

Dashboard has Operations Map     YES
Dashboard has Critical Alerts    NO
Dashboard has Attendance         YES
```

The tenant **cannot enable anything above that ceiling**.

Then the tenant manages its own staff permissions:

```text
Tenant purchased:
Dashboard = YES
Reports = YES
Grievances = YES

Tenant Admin:
Dashboard = YES
Reports = YES
Grievances = YES

Supervisor:
Dashboard = YES
Reports = YES
Grievances = NO

Driver:
Dashboard = NO
Reports = NO
Grievances = NO
```

Conceptually:

```text
Effective User Access
=
Zigma Tenant Entitlement
AND
Tenant User Permission
```

So even if a tenant administrator somehow assigns:

```text
Route Optimization = YES
```

to a staff member, if Zigma has configured:

```text
Tenant Route Optimization = NO
```

the effective result remains:

```text
NO
```

This is a very strong universal model.

# 11. Why I strongly recommend separating Data Scope

This is one of the most important architectural concepts.

Consider this configuration:

```text
Tenant:
Erode Municipality

Allowed Data:
State = Tamil Nadu
District = Erode
Local Body = Erode Corporation
```

Now Zigma configures:

```text
Operations Map = YES
Ward filter = NO
```

If UI configuration and data scope were the same thing, the system could mistakenly interpret:

```text
Ward filter hidden
```

as:

```text
No ward restriction
```

Those are completely different things.

### Feature configuration answers:

> **What can the tenant use?**

Example:

```text
Can see map? YES
Can see Ward filter? NO
Can see Grievance widget? YES
```

### Data scope answers:

> **Whose data can the tenant see?**

Example:

```text
State:
Tamil Nadu

District:
Erode

Local Body:
Erode Corporation

Allowed Wards:
1–60
```

They must remain independent.

---

# 12. Example showing why this matters

Suppose a client tells you:

> “Don't show me State and District filters. We're only operating in Erode Corporation, so they're useless.”

You configure:

```text
State Filter     OFF
District Filter  OFF
Local Body       OFF
Ward Filter      ON
```

But their data scope remains:

```text
Tamil Nadu
  ↓
Erode
  ↓
Erode Corporation
```

Their APIs are automatically constrained to Erode Corporation.

The hidden filters simply mean:

> “Don't make the user select something that can never change.”

It does **not** mean:

> “Remove the Erode restriction.”

This is why those concepts must be separate.

---

# 13. A more important security example

Imagine:

```text
Tenant A:
Erode

Tenant B:
Coimbatore
```

Tenant A has:

```text
District Filter = OFF
```

If database security depended on that filter, Tenant A could potentially call:

```text
/api/dashboard?district=Coimbatore
```

That must never work.

Instead:

```text
Authenticated tenant
        ↓
Tenant Data Scope
        ↓
Erode only
        ↓
API query constrained
```

UI filtering is applied **after that**.

So:

```text
SECURITY SCOPE
≠
UI FILTER
```

This separation is non-negotiable for a proper multi-tenant platform.

# 28. When is custom development genuinely required?

Only when the client asks for a capability that does not exist.

For example:

> “Show a heat map of missed collections based on the last 90 days.”

If IWMS doesn't currently have:

```text
Missed Collection Heatmap
```

then that's genuinely new functionality.

You develop:

```text
dashboard.missed_collection_heatmap
```

once.

After that, future tenants can configure it.

This is the fundamental SaaS pattern:

```text
First requirement
→ product enhancement

Future customers
→ configuration
```

not:

```text
Customer A
→ custom fork

Customer B
→ another custom fork

Customer C
→ another custom fork
```

This helps when introducing new widgets/settings later.

For a newly introduced feature you can decide:

```text
Existing tenants:
default OFF

New Enterprise tenants:
default ON
```

without breaking deployed clients.

# 36. Final architecture I recommend

Your tenant customization engine should ultimately look like:

```text
                   IWMS PRODUCT REGISTRY
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
      Modules            Screens           Widgets
                                             │
                                             ▼
                                  Controls / Behaviors
                           │
                           ▼
                    Package Templates
                           │
                           ▼
                    Tenant Overrides
                           │
           ┌───────────────┼────────────────┐
           │               │                │
           ▼               ▼                ▼
      Entitlements       Layout         Behaviour
                           │
                           ▼
                    Resolved Tenant UI
                           │
                           ▼
                    Tenant User System
                           │
                           ▼
                 User-specific permissions
```

With **Data Scope alongside this**, not inside it:

```text
Tenant
│
├── Product Configuration
│
└── Data Scope
```

## The decision I would lock in

For your question #12, I would choose **a hierarchical version of B + selective C**.

Meaning:

> Configure **major widgets + meaningful business subfeatures + genuinely useful UI controls**.

Not only major widgets, because your clients may legitimately want to hide layers, filters, fullscreen, GPS counts, etc.

But not every UI element either, because that becomes unmaintainable.

So your hierarchy becomes:

```text
MODULE
  ↓
PAGE
  ↓
SECTION
  ↓
WIDGET
  ↓
SUBFEATURE / CONFIGURABLE CONTROL
  ↓
BEHAVIOR SETTINGS
```

And **layout is separate**, while **data scope is completely separate**.

That gives you the flexibility you're looking for without creating millions of hard-coded tenant combinations.
